# resolve-capability design

Status: draft for review. Nothing here is implemented yet.

## Problem

Each pstack skill and playbook still says how to do a thing in Cursor: `Task`, `AskQuestion`, `/loop`, cloud agents, Bugbot, `agent-transcripts/`. The rewrite so far swaps those names for the names of one harness or another, one skill at a time. The same knowledge ("how do I start a helper agent here?") ends up in many files, and every change in Orca, Claude Code, or Codex means editing all of them again.

## Idea

Three layers, each owning one kind of change.

| Layer | What it holds | Owner | Changes when |
| --- | --- | --- | --- |
| 1. Intent | `poteto-mode`, the playbooks, the other skills. They say what to do and why, and name each thing they need from the environment by its capability name. They name no product. | pstack | The way of working changes |
| 2. Adapter | `resolve-capability`. It says how each capability is done in each environment, what to do when it cannot be, and which steps are exact. | pstack, shipped, checked in CI | Orca, Claude Code, Codex, or Grok adds or changes a feature |
| 3. This computer | `select-model`, generated by `/setup-pstack`. It records which products, models, and environments exist here and what the user prefers. | the user | `/setup-pstack` runs |

Layer 1 and layer 2 are shipped together, so layer 1 reads layer 2 by the same relative path that bundled skills already use: `../resolve-capability/SKILL.md`. Nothing is copied into the user's home, so layer 2 cannot go stale there. Layer 3 stops copying `references/` from the generator. It keeps the inventory and the preferences, and its inventory points at the layer 2 files that apply on this computer.

The model running a task reads layer 3 and the layer 2 index once at the start, as it reads `select-model` today. It decides which mechanism to use for each capability. It reads a layer 2 reference file only when it reaches a capability that needs one.

## The vocabulary

A capability is one thing a playbook step needs from its environment. The names are closed: a skill uses these names and no others. A new need is added here first.

Each capability has one of four states in a given environment.

- `native`: the harness does it with its own tool.
- `via <product>`: it needs a product that may or may not be here, such as Orca.
- `by hand`: no tool exists, so do it with the shell and the reply.
- `skip`: drop the step and say so in one line.

What this does not cover, on purpose:

- **Frontmatter and `disable-model-invocation`** (51 rows). Harness-neutral, kept as written.
- **Cursor UI wording** (50 rows). Custom Modes, the sidebar, and plugin-install screens are skipped. The slash prefix (`/name` in Claude Code, `$name` in Codex) is a one-line note in the user guide, not a capability.
- **URLs and the install source** (11 rows) and the plugin manifests. A packaging decision, made once.
- **Features removed already** (Automations event triggers, `make-bot-ui`, the benny pack). They are recorded in `docs/removed-cursor-features.md`.

Two rules sit on top of the table.

1. **The model chooses among the mechanisms; the adapter says exactly how to run the one it chose.** Where an action cannot be undone (`orca worktree rm`, merging a PR, deleting a branch), the adapter gives the exact command and the reading model does not improvise it.
2. **Where an environment differs in structure and not only in name, the playbook states the intent and the invariants, and the adapter's reference file holds the procedure.** The Orca coordinator loop (run, worker, `check --wait`, ack, release) is the main case, and `orchestrate.md` leans on it.

## How a skill uses it

A step names the capability in backticks and states what it needs, not how:

> Start `spawn-worker` seats for each runner, read-only, and wait for all of them with `wake-on-event`.

`poteto-mode` reads `../resolve-capability/SKILL.md` at the start of a task. Its `SKILL.md` is an index of about 100 lines: how to tell which environment this is, then one line per capability. Procedures live in `references/` (`orca-workers.md`, `orca-automations.md`, `claude-code.md`, `codex.md`, `grok.md`, `plain.md`) and are read only when a step reaches that capability. A long-running playbook re-reads the index when it resumes.

A lint keeps product names out of layer 1: no `Task`, `AskUserQuestion`, `TodoWrite`, `update_plan`, `orca <command>`, or `gh` command in a rewritten skill outside the adapter and the generator's references. The existing `check-orca-commands` check covers the adapter's `orca` lines against the Orca snapshot.

## What changes in what exists

- **New:** `skills/resolve-capability/` (index and references). The rows in `CURSOR-DEPENDENCIES.md` become the source for its mappings, and each row's status turns to `done` when its capability is in the adapter.
- **Replaced:** `skills/orca-harness/`. Its content is regrouped by capability. It stays until the last skill stops pointing at it.
- **Smaller:** the `poteto-mode` Subagents section keeps the choosing rules and hands the mechanics to the adapter. The rewritten cross-model skills swap `Agent`, `spawn_agent`, and `orca` lines for capability names.
- **Generator:** stops copying `references/`. Adds a capability survey to `inventory.md`: whether `gh` is logged in, whether a saved Orca environment exists, whether Orca automations are available, and which review bots a repository uses.
- **Later:** the playbooks (Unit 4) and the remaining skills (Unit 5) are rewritten in this vocabulary. Playbook work is on hold until this design is settled.

## Checks

1. **Table or judgment.** Run the same playbook step with the mechanisms table and with capability names alone, on Sonnet at low effort, on Opus, and on Codex. Count skipped steps and wrong tools. Keep the table where the counts differ. The first `verify-pstack` proof already showed Sonnet at low effort skipping an Orca check that the text left to its judgment.
2. **Per capability and environment.** One real run for each cell of the table that names a command, through `verify-pstack`. Cells marked `?` are filled in or removed first.
3. **Lint.** The product-name ban above.
4. **Long runs.** One multi-hour playbook (`autopilot-full` or `orchestrate`) to see whether the model still follows the adapter after the index has scrolled out of its context.

## Open points

4. How the plain, no-Orca mechanisms for `coordinate-workers` and `wake-on-event` should be tested.
5. Whether `choose-model` stays a capability in this table or remains only `select-model`.
